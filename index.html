Version control is a time machine for your work. Git is the machine; GitHub is where you park it so others can climb aboard. Let's watch how it actually works.

01 / THE PROBLEM

Ever named a file final_v2_REALfinal.docx?

That messy pile of copies is version control done by hand — and it falls apart fast. You can't tell what changed between versions, you can't safely undo a mistake, and if two people edit at once, someone's work gets overwritten.

Git solves this. Instead of saving whole copies, it records each change you make as a labelled snapshot you can jump back to at any time.

Real life

A video game save point. Before a boss fight, you save. If you lose, you reload from that exact spot — no progress before it is lost.

In Git

A commit. Each commit is a save point for your project. You can reload any earlier one, forever.

03 / GIT vs GITHUB

Same word, two different jobs

Beginners mix these up constantly. Keep them straight and the rest is easy.

Git

The tool on your computer

Git runs locally. It tracks changes, makes commits, and manages branches even with no internet. Think of it as the camera taking the snapshots.

GitHub

The website that hosts it

GitHub stores your project online so a whole team can share it, review changes, and work together. Think of it as the shared photo album in the cloud.

Analogy

Git is to GitHub what Word is to Google Drive. One creates and edits the document; the other stores it online and lets people collaborate. You can use Git with no GitHub at all — but GitHub makes teamwork painless.

04 / TEAMWORK

Push, pull, and staying in sync

When your commits live on your laptop, only you can see them. GitHub is the shared copy in the middle. Two commands move work between your machine and that shared copy:

git push

Upload. Send your local commits up to GitHub so teammates can get them. Like posting your photos to the shared album.

git pull

Download. Bring teammates' latest commits down to your machine. Like refreshing the album to see what others added.

The daily rhythm

Pull → work → commit → push. Pull first so you start from the newest version, do your work, save it as commits, then push to share. Do this every session and you'll rarely hit a conflict.

05 / CHEAT SHEET

The seven commands that cover 90% of it

CommandWhat it does
git initStart tracking a project with Git (do this once).
git clone <url>Copy an existing GitHub project onto your computer.
git add .Stage your changes — pick what goes in the next snapshot.
git commit -m "msg"Take the snapshot with a short note describing it.
git pushUpload your commits to GitHub.
git pullDownload the latest commits from GitHub.
git statusAsk Git what's changed and what's staged. Use it constantly.
Golden rule

Write commit messages a teammate (or future-you) will understand. "fix login crash on empty password" beats "stuff" every single time.

Save early, save often, and never fear breaking things.
